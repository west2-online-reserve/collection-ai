# 校园·if 恋：项目说明与开发问题记录

## 一、项目概述与作业要求对应

《校园·if 恋》是一个使用 Python 编写的终端文字恋爱模拟游戏。玩家扮演刚进入大学的新生，在社团、图书馆和校外咖啡店依次遇见学姐、小白、姐姐。选择一位角色后，通过聊天、送礼改变好感度，最终触发成功或失败结局。

项目练习的重点是把条件判断、循环、类、字典、模块和文件读写组合成可以运行的完整流程。游戏采用单角色路线：选中角色后，后面的相遇场景被跳过，当前一局不能在三位角色之间自由切换。

作业来源：[校园·if 恋作业要求](https://github.com/5-bin/learn-AI/blob/main/tasks%282026%29/foundation/Campus_IF_Love/README.md)。要求与实现对应如下：

| 作业要求 | 当前实现 |
| --- | --- |
| 完成 `talk()` | 根据角色和好感度选择对话，读取 A／B 选项并更新数值 |
| 完成 `give_gift()` | 查询礼物效果，调用 `change_affinity()` |
| 补全第二、第三位角色的决定点 | `scene_xiaobai()`、`scene_jiejie()` 返回是否进入路线 |
| 补全主线聊天、送礼操作 | `story_loop()` 组织互动与结局判断 |
| 至少拆分为三个 Python 文件 | 当前有入口、游戏逻辑、剧情数据、存档管理四个模块 |
| 使用 Type Hint | 为函数参数、返回值、角色属性及数据容器添加类型注释 |
| 存档、读档、即时存档 Bonus | 已提供普通和即时两个槽位，可恢复进行中的角色路线；边界见后文 |

原剧本是故事和初始规则参考，实际运行以代码为准。例如剧本中的聊天基础值为 +5、结局阈值为 100；当前实现调整为普通聊天加减 10，并增加好感度 90 时的关键选择。

## 二、环境与运行方法

本次核对环境为 macOS、Python 3.13.15。程序使用 `typing`、`sys`、`json`、`pathlib` 等标准库，无需安装第三方依赖。`game.py` 仍导入了 `random`，但当前对话选择没有使用随机数。这里仅记录已验证环境，不承诺所有旧版 Python 均可运行。

在终端执行：

```bash
cd "/Users/bin/projects/ai-leaning_works/collection-ai-2026/foundation/5-bin/Task 1/Campus_IF_Love_副本"
python3 Campus_IF_Love.py
```

启动菜单的 1—4 分别是开始新游戏、读取普通存档、读取即时存档和退出游戏。新游戏会重置所有角色好感度和当前路线，再播放开场文字。

菜单使用数字字符串；聊天接受 A、B 和小写 a、b。输入时不要额外添加空格，因为程序没有统一调用 `strip()`。送礼需要输入列表中完整的礼物名称。运行时的保存操作会覆盖对应槽位，若需要保留旧进度，应先自行备份存档文件。

## 三、项目结构与模块职责

| 文件或目录 | 职责 |
| --- | --- |
| `Campus_IF_Love.py` | 创建 `Game` 对象，通过 `main()` 启动游戏 |
| `game.py` | 定义 `Character`、`Game`，组织角色互动、菜单、结局和恢复流程 |
| `story.py` | 保存 `DIALOGUES` 对话库和 `GIFT_EFFECTS` 礼物效果表 |
| `save_manager.py` | 确定存档路径，完成 JSON 写入、读取及部分异常处理 |
| `saves/` | 保存普通进度 `save.json` 与即时进度 `autosave.json` |
| `README.md`、`Campus_IF_Love_Story.md` | 原始作业说明及剧本参考 |

调用方向是入口调用 `Game.start()`，游戏逻辑读取剧情数据，并通过存档管理模块访问文件。数据模块不反向调用游戏，因而调整礼物数值或对话文本时通常只需修改数据表。

`Character` 保存姓名、角色描述和好感度，负责聊天、送礼、数值更新及结局状态检查。`Game` 持有角色集合、当前攻略对象和剧情位置，负责决定操作发生的顺序。键为字符串 `"None"` 的角色对象表示尚未选定路线，它不是 Python 的 `None`。

类型注释示例包括 `talk() -> int`、`scene_xiaobai() -> bool`、`current_target: Character`。对话库声明为 `Dict[str, List[Dict[str, str]]]`，礼物表声明为 `Dict[str, Dict[str, int]]`。这些注释帮助理解接口，但不会自动检查运行时输入；存档字段使用 `Any`，仍需要额外的数据校验。

## 四、玩法与核心实现

### 4.1 路线选择与主循环

`start_new_game()` 按学姐、小白、姐姐的顺序调用场景。每个场景选择 `1` 后设置 `current_target`，进入 `story_loop()` 并返回 `True`；否则返回 `False`，让外层继续下一场景。三个场景全部跳过时，输出结束提示，程序自然结束。

这一结构利用嵌套的布尔判断保证路线互斥。当前场景函数把所有非 `1` 输入都视为跳过，因此输入错误也会错过角色，尚未提供重新选择机制。

进入路线后的菜单为：

| 输入 | 操作 |
| --- | --- |
| `1` | 与当前角色聊天 |
| `2` | 展示礼物列表并送礼 |
| `3` | 查看当前好感度 |
| `4` | 覆盖普通存档 |
| `5` | 直接退出程序 |

聊天和送礼完成后，循环检查好感度、必要时进入结局流程，再执行即时保存。查看数值、普通保存以及外层菜单无效输入，只要继续执行到循环末尾，也会触发即时保存。

### 4.2 对话选择与好感度变化

`talk()` 先用 `DIALOGUES.get(self.name, [])` 获取该角色的对话列表。每位角色有五条对话，其中前四条用于日常互动，第五条用于关键节点。

| 聊天开始前的好感度 | 普通对话索引 |
| --- | --- |
| 小于 25 | 0 |
| 25 至小于 50 | 1 |
| 50 至小于 75 | 2 |
| 大于等于 75 | 3 |

索引由本次聊天开始前的好感度决定。选择 A 调用 `change_affinity(10)`，选择 B 调用 `change_affinity(-10)`；输入无效时留在当前对话重试。所有普通对话都采用这套加减规则，不额外分析回答内容。

函数返回本次显示的索引，外层把它写入 `story_line`，同时把角色名写入 `story_block`。例如从 20 分聊天并选择 A 后，好感度成为 30，但保存的索引仍为 0，因为刚才展示的是第 0 条对话。同一阶段重复聊天会显示相同内容。

### 4.3 送礼与数据驱动

`give_gift(gift)` 先读取礼物的 `default` 值，再读取该角色的专属值。专属值优先；没有专属值则使用默认值，默认值也不存在时为 0。最终统一调用 `change_affinity(effect)`，避免重复编写数值更新。

| 礼物 | 学姐 | 小白 | 姐姐 |
| --- | ---: | ---: | ---: |
| 鲜花 | +10 | +10 | +15 |
| 编程笔记 | +5 | +15 | +15 |
| 奶茶 | +20 | +20 | +20 |
| 奇怪的石头 | −10 | −10 | −10 |
| 精致的钢笔 | +20 | +10 | +20 |
| 可爱玩偶 | +10 | +20 | +10 |
| 夜宵外卖 | 0 | +5 | −5 |

“奇怪的石头”只配置 `default: -10`，体现了默认规则的用途。角色循环会拦截不在礼物表中的名称并要求重输；直接调用角色方法传入未知名称则按 0 处理。当前没有金币、库存和赠送次数限制，同一种礼物可以重复赠送。

### 4.4 结局判定

每轮操作后，好感度小于等于 −20 时进入失败退出流程；在 −20 与 0 之间时给出不满提示；大于等于 90 时显示索引 4 的关键对话。关键选择 A 把好感度直接设为 200，显示成功信息并进入退出菜单；B 把好感度设为 80，继续互动，之后仍可再次触发关键选择。

`check_ending()` 只判断当前数值是否已达到结束状态：大于等于 200 或小于等于 −20。它不负责展示关键选项。这个区别也用于读档：已经结束的路线不能继续。

结局退出菜单提供保存和离开两项。选择保存后仍留在该菜单；选择离开时先即时保存再退出。当前成功结局输出通用文字，原剧本中的考研、共同学习等完整后日谈尚未逐段实现。

## 五、存档与读档机制

### 5.1 文件与数据结构

`save_manager.py` 使用 `Path(__file__).parent / "saves"` 定位目录，因此存档位置跟随模块，不依赖启动终端的当前目录。首次保存时创建目录；普通和即时保存分别覆盖各自文件。

`create_save_data()` 把运行中的对象状态转换成四个 JSON 字段。例如在小白线完成一次第 0 条对话并选择 A 后，可得到：

```json
{
    "story_block": "小白",
    "story_line": 0,
    "current_target": "小白",
    "affinity": 10
}
```

| 字段 | 含义与当前用法 |
| --- | --- |
| `story_block` | 开场为 `opening`；选择路线后立即设为角色名，聊天后仍为角色名，送礼后为礼物名 |
| `story_line` | 最近一次普通对话的列表索引；送礼时不会重置 |
| `current_target` | 当前角色的名称，用于找回已有角色对象 |
| `affinity` | 当前角色的好感度 |

写入使用 UTF-8、`ensure_ascii=False` 和四空格缩进，中文保持可读。文件只记录当前角色，没有保存所有角色的数值、对话历史或关键选择位置。因此这是最近互动与角色状态的恢复机制，尚未达到剧本每一句、每个选择点都可以精确恢复的程度。

### 5.2 保存触发时机

手动保存路径是 `normal_save()` → `create_save_data()` → `save_game(auto=False)`。即时保存复用相同结构，只把 `auto` 改为 `True`。

正常聊天或送礼结束后会保存即时进度；结局退出菜单选择离开也会保存。角色主菜单选择 `5` 则直接调用 `sys.exit(0)`，不会新增一次保存，也不会删除此前已保存的进度。选择任一角色路线时，会立即将剧情块设为角色名、剧情索引设为 0；即使尚未聊天或送礼，也可以手动保存并在读档后继续。恢复时会展示该角色索引 0 的对话作为位置提示，不代表此前已经实际进行过这段对话。

### 5.3 读取与继续游戏

启动菜单读取普通或即时槽位，先由 `load_game()` 解析 JSON，再由 `apply_save_data()` 查找角色并覆盖状态。普通读取方法的实际名称是 `load_nomal_save()`，保留了源码中的拼写。

应用数据成功只表示状态已载入，之后仍需 `resume_game()` 检查是否允许继续。如果尚未选择角色、路线已结束或剧情块为 `opening`，它返回 `False`，启动菜单继续等待选择；否则展示最近的对话或礼物信息，进入 `story_loop()`。

读取文件不存在时返回空字典；JSON 损坏或部分文件读取错误也会提示后返回空字典。应用阶段先校验所有必需字段：角色名与剧情块必须为字符串，角色必须存在；剧情索引和好感度必须为整数且排除布尔值，索引不得为负数。对话剧情块必须与当前角色一致，索引不得超过该角色的对话列表范围；其余剧情块只接受 `opening` 或已有礼物名。所有校验通过后才统一更新状态，非法存档不会部分覆盖当前进度。写入阶段也未捕获磁盘或权限错误。

核对时，目录中两个存档均为学姐线、好感度 −20，属于已结束状态。读取后不能继续是结局检查的结果，不能据此判断读档功能整体失效。本次文档编写保留了这两个文件。

## 六、开发问题与解决方式

### 6.1 单文件职责集中，不便独立维护

早期入口、流程及剧情数据放在一起，修改文本时需要在较长的程序中定位，后续加入存档也会继续增加单文件内容。提交 `8ee90cb` 将其拆为入口、`game.py` 和 `story.py`；之后增加 `save_manager.py` 专门处理文件读写。

这一处理明确了数据、流程与存储的职责，也满足了至少三个 Python 文件的要求。提交 `5c9ad12` 继续封装 `main()` 并添加类型注释，使入口和数据传递更容易阅读。

### 6.2 存档需要记录可恢复的状态

仅保存好感度无法知道正在攻略谁，也无法展示最近发生的互动。当前实现使用 `create_save_data()` 集中生成角色、数值和剧情位置，再由普通、即时保存共同调用；读取时按角色名找回对象，而不是尝试直接序列化 `Character` 实例。

提交 `acba097` 引入了保存、覆盖状态和加载的部分实现，`58f724d` 进一步接入完整菜单。`talk()` 返回对话索引，调用方同步记录最近对话，使保存的数据能对应实际展示过的内容。这解决了基本状态恢复的组织问题，但未实现完整剧情检查点。

### 6.3 读取文件之后还需要恢复流程

读出 JSON 并覆盖数值之后，程序仍需决定返回开场、进入互动，还是拒绝继续已结束路线。提交 `58f724d` 增加 `resume_game()`，把状态应用与流程恢复分开，并在启动菜单中根据返回结果决定是否重新等待输入。

同次改动把关键剧情交互放进主循环，让 `check_ending()` 只检查终态；聊天增加 `.upper()` 接受小写选择。源码可以确认这些处理已经存在，但不能据此推断此前必然出现过某种报错。

## 七、当前限制与改进方向

| 当前限制 | 后续可采用的改进 |
| --- | --- |
| 角色主菜单直接退出不额外保存 | 统一退出入口，明确保存策略 |
| 剧情块混用角色名和礼物名，送礼不更新对话索引 | 分离互动类型、场景位置和对话记录 |
| 只恢复最近互动，没有逐句位置和关键选择状态 | 增加稳定的剧情节点与阶段标记 |

| 写入直接覆盖，异常可能中断保存 | 增加写入错误处理及临时文件替换 |
| 场景错误输入会跳过，首尾空格未统一处理 | 统一输入校验并提供重试 |
| 角色描述、原剧本与实际场景有差异 | 对齐设定及最终文案 |

对话剧情块的越界索引（例如 999）和字符串好感度现已在应用阶段拒绝。开场与礼物剧情块的字段关联、写入异常等仍有完善空间，尚不能宣称程序可以安全恢复任意 JSON 文件。
