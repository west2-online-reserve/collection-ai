# 作业 2：知乎话题问答采集 · 完成报告

## 1. 任务与完成情况

**任务**：使用 Selenium 采集知乎话题「编程」（[19554298](https://www.zhihu.com/topic/19554298/top-answers)）下 20 个不同问题，每个问题采集 10 条不同回答，输出 CSV，字段为 `question_id`、`question_title`、`question_content`、`answer_id`、`answer_content`。

**结果**（2026-11-24 真实采集）：

| 指标 | 结果 |
|---|---|
| 不同问题数 | 20 |
| 每题回答数 | 20 题均为 10 条 |
| 总行数 / 不同回答 ID | 200 / 200 |
| 空回答 | 0 |
| 无问题描述的题 | 7（页面本身没有描述，`question_content` 为空字符串） |
| 最后一轮失败题数 | 0 |
| 离线检查 `check_csv.py` | 通过，退出码 0 |
| 人工抽查 | 随机 3 条，开头与结尾均与网页一致 |

结果文件：[data/zhihu_answers.csv](data/zhihu_answers.csv)。

## 2. 整体思路

```
接管已登录的 Chrome ──► 话题精华页滚动收集 20 个不同问题
                                │
              ┌─────────────────┘
              ▼
   逐题打开问题页 ──► 标题 ──► 描述（有则展开读取，无则为空）
              │
              ▼
   滚轮触发懒加载，按回答 ID 去重取前 10 条 ──► lxml 清洗为纯文字
              │
              ▼
   本题满 10 条 → 立即追加写入 CSV；不足 → 记入失败，继续下一题
              │
              ▼
   结束：读回比对 + 统计；另用 check_csv.py 离线验收
```

几个设计取舍：

- **先列表、后详情**：先把 20 个问题的 ID、标题、链接收集齐，再逐题处理，两段逻辑分别封装成 `collect_questions()` 和 `crawl_question()`，便于单独测试。
- **以 ID 去重**：话题页的卡片是“回答”，同一问题可能出现多张卡片，所以按问题 ID 去重；回答同样按 `answer_id` 去重。
- **逐题保存**：每题成功后立刻追加写入，中途中断不会丢失已完成的题，并以此为基础实现断点续采。
- **失败分级**：单题失败（超时、回答不足）跳过继续；访问受限和写文件失败直接停止，避免在异常状态下继续请求或产生残缺文件。
- **不凑数**：回答不足 10 条的题整题不写入，不用空值或重复数据补齐。
- **独立验收**：采集脚本之外另写一个只读 CSV 的检查脚本，不依赖浏览器即可复核结果。

## 3. 遇到的主要问题与解决过程

### 3.1 登录方式：为什么最终没有用 Cookie 保存登录状态

**最初方案**：由 Selenium 新开 Chrome，把之前导出的 Cookie JSON 注入浏览器，运行结束再把最新 Cookie 写回文件。

**遇到的问题**：话题列表页可以正常访问，但打开任何问题详情页都返回知乎业务错误 `40362`（“您当前请求存在异常，暂时限制本次访问”）。排查过程如下（完整排查记录保存在本地报告中，未随仓库提交）：

| 对照 | 结果 |
|---|---|
| 普通浏览器手动打开同一问题 | 正常 |
| Selenium 新开窗口 + 注入 Cookie 后打开详情 | `40362` |
| 从话题页点击标题链接进入（站内导航） | `40362` |
| 不注入 Cookie，在 Selenium 新开的窗口里直接人工登录 | 仍为 `40362` |
| **手动启动一个带专用资料目录的 Chrome 并登录，Selenium 通过调试端口接管** | **详情页正常** |

**结论与选择**：

- “换一份 Cookie / 重新登录”没有解决问题，所以 Cookie 本身不是充分解释；`40362` 的确切触发原因（自动化特征、会话状态、频率或时间因素）**未能确定**，本作业不对根因下结论。
- 最终改为“**手动启动 Chrome + `debugger_address` 接管**”：浏览器由人启动、人登录，登录状态由 Chrome 自己保存在专用资料目录 `private/browser-profile` 中，下次启动自动沿用。
- 这样做还有两个附带好处：不再需要读写 Cookie 文件，凭据不会以明文 JSON 的形式出现在项目里；也不需要处理 Cookie 过期与刷新。
- 资料目录整体被 Git 忽略（`private/.gitignore` 内容为 `*`）。

### 3.2 详情页标题等待超时：页面里有两个同名标题

接管成功后，等待 `h1.QuestionHeader-title` 可见时超时，但浏览器里标题明明可见。通过调试端口只读检查 DOM 发现：页面有**两个**匹配元素，第一个属于顶部吸顶栏，处于隐藏状态；而 `visibility_of_element_located` 内部用 `find_element`，只检查第一个匹配。改为容器限定选择器 `.QuestionHeader h1.QuestionHeader-title` 后唯一匹配，问题解决。**教训**：等待超时不一定是“加载慢”，先确认选择器匹配到的是哪个元素，而不是盲目加长等待时间。

### 3.3 问题描述：折叠、无按钮、完全没有描述三种情况

| 页面情况 | 早期代码的表现 | 处理 |
|---|---|---|
| 描述折叠，有“显示全部”按钮 | 只读到截断文字 | 点击按钮后再读全文 |
| class 带 `--collapsed`，但没有按钮（描述很短） | 等待按钮超时，整题失败 | 先用 `find_elements` 判断按钮是否存在，存在才点击 |
| 问题根本没有描述 | 等待描述元素超时，重试 3 次后失败 | 先用 `find_elements` 判断描述元素是否存在，不存在则记为 `""` |

**共同原则**：页面上**可能不存在**的元素，用 `find_elements`（无匹配时返回空列表）判断，而不是用必然超时的 `wait.until`。

### 3.4 回答的翻页（懒加载）：只能拿到 5 条

问题页初始只渲染 5 条回答，需要向下滚动才会加载更多。这是本作业耗时最多的问题，尝试过程如下：

| 尝试 | 结果 |
|---|---|
| `window.scrollTo` 直接跳到页面底部 | 不加载，仍为 5 条 |
| 从页面顶部用滚轮连续滚 5×800 像素 | 只滚到约 4000 像素处，未到触发区，更差 |
| 怀疑窗口在后台（页面不可见）导致不加载 | 窗口前台可见时仍然只有 5 条，排除 |
| 人工慢慢滚动 | 可以加载，说明需要**真实的滚轮事件经过列表末尾附近** |
| **先 `scrollTo(0, scrollHeight - 2500)`，再用 `ActionChains` 滚轮 5×400 像素** | **稳定加载到 10 条以上** |

正式运行中又发现个别题偶尔一次滚动没有触发加载。于是加入**连续失败计数**：一次等待超时后再试一轮，连续 2 次超时才判定“没有更多回答”；总滚动轮数仍有上限，避免无限循环。正式采集中第 17 题出现了“第 1 次未加载出新回答”，随后重试成功。

> 附带问题：调窄浏览器窗口做实验时，登录头像按钮超出视口，登录检查的“可见”等待超时。登录检查改为 `presence_of_element_located`（只要求元素存在于 DOM），与窗口大小无关。

### 3.5 回答正文清洗

直接用 Selenium 的 `.text` 会混入广告卡片、“推广”链接卡片和视频播放器的文字。改为取回答正文的 `outerHTML`，用 lxml 删除广告/MCN 卡片容器与视频播放器节点后，按段落拼接纯文字，段落间用换行分隔。

### 3.6 批量采集的稳定性：失败分级、逐题保存与断点续采

- **失败分级**：只捕获 `TimeoutException`（元素超时、回答不足）并记入失败列表后继续；`RuntimeError`（检测到 40362 访问受限）和 `OSError`（写文件失败）不捕获，让程序停止。
- **限速**：题与题之间随机等待 3～6 秒；等待放在循环开头，避免失败题用 `continue` 跳过限速。
- **逐题追加**：最初是全部采完再一次性写入，中途失败会丢失全部数据；改为每题成功后用追加模式写入。
- **断点续采**：实际按 Ctrl+C 中断后发现，重新运行时开头的写表头语句（`"w"` 模式）会清空已有数据。改为：
  1. 文件不存在才新建并写表头；存在则读回，用 `Counter` 统计每题已保存行数；
  2. 已有 10 行的题直接跳过（放在限速等待之前，不白等）；
  3. 其他题重新采集时只追加未保存过的 `answer_id`；
  4. 结束时把“旧行 + 本轮新行”与读回的文件比较。

  正式采集正是分多次完成的：最后一次运行跳过已完成的 4 题，补采其余 16 题。

### 3.7 环境问题：Chrome 自动更新导致驱动版本不匹配

某次运行报 `SessionNotCreatedException: This version of ChromeDriver only supports Chrome version 158, Current browser version is 157`。原因是 Chrome 在后台更新到 158，Selenium Manager 按磁盘上的版本选择了 158 的驱动，而 9222 端口上仍是更新前启动的 157 进程。完全退出该 Chrome 并重新启动即可。

### 3.8 结果验收：检查脚本本身也要验证

`check_csv.py` 把数量、题内与全局重复、空回答、同题标题/描述一致性的问题收集到列表，全部通过时退出码为 0，否则逐条列出并以退出码 1 结束。为证明检查确实有效，用真实数据构造了 7 份故意出错的副本（删一行、题内重复、跨题重复、空白回答、标题不一致、只剩 19 题），每种都被正确发现；再随机抽样 3 条与网页人工对照。

## 4. 运行方法

### 4.1 环境

- Python 3.13（在 3.13.15 上验证），macOS，Google Chrome。
- 直接依赖见 [requirements.txt](requirements.txt)：`selenium==4.52.0`、`lxml==6.1.3`；其余为标准库。ChromeDriver 由 Selenium Manager 自动下载。

在 `Task 2` 目录下：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r 作业2_知乎话题/requirements.txt
```

### 4.2 启动浏览器并登录

**必须在 `Task 2` 目录下执行**（`$PWD` 是当前目录；在其他目录执行会在错误位置新建一份空资料，需要重新登录，且该位置可能不在 Git 忽略范围内）：

```bash
open -na "Google Chrome" --args --remote-debugging-port=9222 --user-data-dir="$PWD/作业2_知乎话题/private/browser-profile" --no-first-run "https://www.zhihu.com/"
```

首次使用在该窗口手动登录知乎。确认调试端口可用：

```bash
curl -s --noproxy '*' http://127.0.0.1:9222/json/version
```

### 4.3 采集与检查

```bash
.venv/bin/python 作业2_知乎话题/crawl.py
```

若脚本提示登录状态未确认，在浏览器中登录后回到终端按回车。可随时 Ctrl+C 中断，重新运行即从断点继续。运行结束后会等待按回车再断开连接。

结果验收所用的离线检查脚本 `check_csv.py`（见 3.8 节）保留在本地，未随仓库提交。

## 5. 输出文件

- `data/zhihu_answers.csv`：采集结果，每行一条回答，UTF-8 编码。

  | 字段 | 含义 |
  |---|---|
  | `question_id` | 问题 ID（问题链接 `/question/<ID>` 的最后一段） |
  | `question_title` | 问题标题 |
  | `question_content` | 问题描述全文；问题无描述时为空字符串 |
  | `answer_id` | 回答 ID，链接为 `https://www.zhihu.com/question/<question_id>/answer/<answer_id>` |
  | `answer_content` | 清洗后的回答纯文字，段落之间用换行分隔 |

- `data/zhihu_failures.csv`：本轮失败的题（`question_id`、`question_title`、`reason`），每次运行结束覆盖写入；无失败时只有表头。
- `data/sample_question.json`：早期单题调试样本，不属于最终结果。

## 6. 限制与未解决事项

- **40362 根因未确定**：换用接管方式后访问恢复，但没有隔离出具体触发因素，不保证长期稳定；脚本检测到该提示会停止。
- **只保存纯文字**：图片、视频、公式图片不保存；清洗规则依赖当前页面结构，知乎改版后选择器可能失效。
- **“前 10 条”不固定**：取决于采集时页面的默认排序和加载结果，不同时间运行可能得到不同回答。
- **部分写入补齐只做过离线测试**：真实运行中逐题整批写入，尚未出现“某题只写了几行”的情况；该分支只在模拟数据上验证过。
- **人工抽查仅 3 条**：其余内容的正确性依赖清洗逻辑与结构检查。
- 需要登录的知乎账号；采集已限速，但不保证不会再次触发访问限制。
